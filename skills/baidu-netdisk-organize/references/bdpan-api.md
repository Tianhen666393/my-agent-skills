# 百度网盘开放平台接口要点

动手前读这一页，能省掉大量试错。

## 结论的有效性

下面所有内容都是 **2026-10-05** 在本机、用个人体验通道实测的结果，测试条件：Windows、Python 3.11、账号为超级会员。百度网盘是外部服务，这几条**随时可能变，不要当成永久事实**。

## 动手前复验

每次动手前花一两分钟跑这几条，成本很低，能避免整套流程白跑：

1. **token 是否还有效、权限范围是否仍是全盘**

   ```bash
   python scripts/bdpan.py whoami
   python scripts/bdpan.py ls --dir "/"
   ```

   `whoami` 应返回账号名；`ls` 应能列出网盘根目录的真实文件夹。若只能看到 `/apps/...`，说明权限范围变了，整套做法都要重新设计。

2. **缩略图尺寸是否还能改**

   ```bash
   python scripts/bdpan.py metas --fsids "<任意图片 fs_id>" --size 1600
   ```

   拿返回的链接下载一次，确认能拿到图片且尺寸明显大于默认的 850 宽。若改尺寸后拿不到图，就退回默认尺寸或改用原图。

3. **按目录递归扫描是否完整**

   对同一个目录，比较 `walk` 的条目数和 `ls` 单层看到的子项数量级是否合理。若某目录 `walk` 结果异常少，说明接口行为变了，按《变更记录》的方式记录并另找办法。

只有出现与记录不符的现象时才需要更新本文件；一切如常就不用动它。

## 鉴权

个人体验通道，不需要企业认证，也不需要自己创建应用。官方授权链接：

```
https://openapi.baidu.com/oauth/2.0/authorize?response_type=token&client_id=QHOuRXiepJBMjtk0esLhrPoNlQyYd0mF&redirect_uri=oob&scope=basic,netdisk
```

- 用户在浏览器打开、登录、点"授权"后，页面跳转到 `oauth/2.0/login_success`，**token 只出现在地址栏 `#` 之后**（形如 `#expires_in=2592000&access_token=123.xxx...`），页面正文不显示。用户找不到时直接告诉他去地址栏找。
- `scope=basic netdisk` 就是"在您的百度网盘创建文件夹并读写数据"。
- 有效期 30 天（`expires_in=2592000`）。
- 官方声明：开放平台目前仅限企业开发者注册调用，个人通道的密钥仅供测试体验、会不定期变更，不要用于正式环境。用完应当解除授权：`passport.baidu.com/v6/appAuthority`。
- 拿到后放进环境变量 `BAIDU_NETDISK_ACCESS_TOKEN`，不要落盘到清单或日志里。

### 权限范围

这个体验 token 实测可以访问**整个网盘**，不受"新应用只能访问 `/apps/{应用名}`"的限制，根目录能直接列出来。

反过来，**自己申请开放平台应用反而不行**：2026-06-03 之后创建的应用，`filemanager`、`meta`、`move`、`download`、`listall`、`precreate` 等接口只能访问 `/apps/{应用名}` 一个目录；未上线审核的应用还限制 10 次/小时。所以不要走自建应用这条路。

## 端点

基址 `https://pan.baidu.com/rest/2.0/`，所有请求都要带 `access_token`。

| 用途 | 方法 | 关键参数 |
| --- | --- | --- |
| 列单层目录 | `xpan/file?method=list` | `dir`（绝对路径，中文和 `/` 都要 URL 编码）、`limit`、`start`、`order` |
| 递归列目录 | `xpan/multimedia?method=listall` | `path`、`recursion=1`、`limit`（可用 10000）、`start` |
| 文件信息 / 缩略图 | `xpan/multimedia?method=filemetas` | `fsids`（JSON 数组字符串，**每批 ≤50**）、`thumb=1` |
| 新建文件夹 | `xpan/file?method=create` | **必须 POST 表单**（参数放 body）；`path`、`size=0`、`isdir=1`、`rtype=0`（重名返回冲突，幂等） |
| 移动 | `xpan/file?method=filemanager` | `opera=move`、`async=0`、`filelist=[{"path":..,"dest":..,"newname":..}]` |
| 用户信息 | `xpan/nas?method=uinfo` | — |
| 容量 | `xpan/nas?method=quota` | — |

`listall` 与 `filemetas` 的返回里，`category` 取值：**1 视频、2 音频、3 图片、4 文档、5 应用、6 其他、7 种子**。

## 限流与稳定性

- 连续快速调用十几次就会返回 `errno=31034 hit frequency limit`。调用之间留 8~10 秒，遇到 31034 等 30 秒重试。
- **全盘 listall 分页不可靠**：实测网盘约 26 万条时，一次性翻页扫出来的图片数比按目录扫少了约 25%。整理统计一律逐目录扫，单目录通常一页就返回完（`has_more=0`）。
- `listall` 的 `category` 参数不起过滤作用，返回的是全类型，要本地按 `category` 字段筛。

## 缩略图

`filemetas?thumb=1` 返回的 `thumbs[0]` 里有 `icon`、`url1`~`url4` 五个尺寸，其中 `url3` 最大（默认 `size=c850_u580`）。

链接里的 `size` 参数可以直接改：

```
size=c850_u580  →  size=c1600_u1600
```

改完仍然有效。实测手机截图能拿到 1260×2800、约 130 KB 一张。**做本地分类和以图搜图都用这个预览图就够了，不必下载原图**，流量能压到十分之一以下。

注意缩略图链接带签名，有效期 8 小时，过期要重新取。

## 移动的注意点

- `filemanager` 的 `ondup` 默认是 `fail`，目标重名会直接失败。批量移动前先确认目标目录没有同名文件，或显式改成 `newcopy`。
- `dest` 只写目标目录，文件名用 `newname` 指定。
- 移动是服务端操作，不产生下载流量，几万个文件也很快；但仍要按限流节奏分批（每批 100 条左右）。

## 本 skill 不允许做的事

- 不允许调用删除类接口（`filemanager opera=delete`）。只移动，不删除。
- 不允许把 `隐私敏感/`、`相机照片/` 或任何隐私图片上传到联网服务。
- 不允许把 token 写进清单、日志、脚本或任何会留在网盘/仓库里的文件。

| 2026-10-05 | `create` 的提交方式 | GET 提交报 `errno=2`，必须用 POST 表单把参数放 body | 稳定复现 |
| 2026-10-05 | `create` 的 `rtype=1` | 目录已存在时**不报错，而是静默新建** `<名字>_YYYYMMDD_HHMMSS`，会多出一堆空目录。幂等创建要用 `rtype=0` | 稳定复现（已实际踩到） |
| 2026-10-05 | `filemetas` 的 `fsids` 批量上限 | 一次传 100 个 fsid 时拼出的 URL 超过服务端长度限制，返回 **HTTP 400**；降到 50 个一批后正常。（94 个曾经成功过，临界值在 50~100 之间，按 50 用最稳） | 稳定复现 |
| 2026-10-05 | `filemetas` 的 `fsids` 写法 | **必须是纯数字数组** `[123,456]`。写成字符串数组 `["123","456"]` 会返回 `HTTP 400 {"errmsg":"fsids error","errno":2}` | 稳定复现（2 个、50 个都复现） |
| 2026-10-05 | `filemetas` 返回的 `thumbs` | 是**字典** `{icon,url1,url2,url3,url4}`，不是数组；字段名也是 `filename` 而不是 `server_filename` | 稳定复现 |
| 2026-10-05 | `filemanager opera=move` 的返回值 | 顶部 `errno` **不能代表整批成功**：实测 100 条一批，顶部 `errno=0` 时仍有约 9.5% 的文件没被移动；顶部 `errno=12` 时逐文件 `info[].errno` 可能全是 `-9`（文件不存在），但把其中任一文件单独移动却成功。**必须读 `info[]` 逐条判断，未成功的逐个重试。** 移动完成后一定要重新扫描源目录核对，不能信返回码 | 稳定复现 |
| 2026-10-05 | **批量移动会放错目录** | 一次 1160 条、目标有 6 种时：只有第一批 100 条进了各自的目标，其余 1060 条全部被塞进其中一个目标（`其他/`）**并保留原目录结构**（变成 `其他/DCIM/Camera/xxx.jpg`）。同一次会话里单文件移动和 2 文件移动都完全正确。**结论：多文件批量移动不可用，一律用 `--per-file` 逐个移动** | 稳定复现（已造成一次事故并回滚） |
| 2026-10-05 | **`listall` 会把同一条目重复列出** | 一次扫描里同一个 `path` 出现 2～4 次：实测 `/怀化学院文档` 返回 159,502 条，其中只有 125,518 个不同路径，多出 33,889 条。**任何统计、去重、体积计算之前必须按 `path` 去重。** 后果很严重：同一次分析里，真实重复只有 5.62 GB，没去重的话会算成 48.63 GB（夸大约 9 倍），体积也会从 105 GB 虚报成 148 GB | 稳定复现 |
| 2026-10-05 | **`listall` 会返回已经不存在的幽灵条目** | 扫描到的两个 `.zip`（`意科USB虚拟串口驱动.zip`、`USB虚拟串口驱动.zip`）在源目录里早已不存在——用户早已把压缩包解压成同名文件夹并删掉了原包。移动时反复报 `-9 文件不存在`，查源目录才发现根本没有这个文件。**结论：扫描数据可能过期；批量移动出现无法解释的 `-9` 时，先去 ls 一下源目录，别一直重试** | 稳定复现 |
| 2026-10-05 | 移动时的重名策略 | 默认 `ondup=fail` 会在**目标目录已有同名文件**（哪怕内容不同）时直接失败。合并两个结构相似的目录时，大量同名不同内容的文件（例如不同版本编译出的同名 `.d`）会全军覆没——实测 446 个文件里 438 个因重名被拒。**合并目录时一律用 `--ondup newcopy`**，代价是重名文件会被加上 `(1)` 后缀 | 稳定复现 |
| 2026-10-05 | 单文件移动的成功率 | 即便逐个移动，单次成功率也不稳定，实测同一批里约一半首次失败、重试后成功。`--per-file` 已内置 3 次重试；**移动后必须用 `filemetas` 按 fs_id 复查当前位置**，不要靠目录列表判断（列表有缓存，会骗人） | 稳定复现 |
