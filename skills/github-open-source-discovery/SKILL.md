# GitHub 开源项目寻宝

## 触发与边界

仅在用户明确使用「GitHub 开源项目寻宝」「开源项目寻宝」或等价表述要求开始检索时执行。只是讨论、引用、转述这些词时不触发。

## 检索与推荐底线

- 优先查看官方 GitHub 仓库、README、最近提交、许可证和 Star 数据，不能仅凭第三方文章介绍下结论。
- 区分热门趋势与适合用户的推荐，不能因为热门就直接视为适合用户。
- 输出项目链接、核心功能、适用场景、上手难度、活跃度及推荐理由。
- 用户提供文章或网址时，先读取其内容，再核对文中项目的官方仓库。
- 动态数据注明查询日期；只推荐或介绍不自动安装，只有用户明确要求安装时才执行安装。
- 下述流程及 `references/字段与目录规范.md` 统一规定记录格式、检索口径和复核机制，不另立一套。

## 每轮流程

先说明本轮检索口径与将要改动的文件，等用户确认后再访问网络或写入文件。

1. **先复核**：读 `项目总目录.xlsx` 与 `待观察项目.md`，按复核优先级取本轮到期项目（每轮上限 5 个），更新热度、推送时间、release、许可证与状态。
2. **再检索**：覆盖两个方向——① 不限方向的高星或趋势项目；② 电赛与电子信息相关项目。两个方向各自入选 0～5 个，没找到就如实记 0，不得凑数，也不得用同一批项目充作两个方向。
3. **核验**：用 GitHub API（`https://api.github.com/repos/{owner}/{repo}` 与 `/contents`）配合原始 README、LICENSE，核实链接、维护状态、开源范围与许可证。API 返回 `NOASSERTION` 或缺省时，直接查仓库自带的许可证文件。
4. **写入**：按 P 序号规则追加详情条目、更新待观察清单，再运行 `python docs\github-projects\tools\build_catalog.py` 重建 `项目总目录.xlsx`。
5. **校验**：确认序号唯一、目录行与详情条目一一对应、详情定位可解析。
6. **汇报**：写明两个方向各自的筛选口径、查看的候选数、入选数（为 0 也要说明原因），并给出 1～3 个最值得深入学习的项目。

## 硬约束

- **只追加不覆盖**：历史条目一律保留。以仓库 URL 作为唯一标识，同一仓库在目录中只占一行，再次出现时更新该行并追加复核记录。
- **不编造**：仓库级「已核验」只代表元数据与仓库文件已核对，不代表做过本地编译、烧录或实机测试。未验证的指标写「待核验」或「无法核验」。
- **许可证与安全边界**：按仓库实际声明记录，注意混合许可；项目自带的使用限制必须显著写出。
- **动态数据标日期**：stars、forks、榜单排名一类快照必须注明查询日期；整轮只取一次运行日期并全程沿用。
- **数量对齐**：宣布写入几个项目之前，先核对最终候选清单，确保宣布数与实际写入数一致。

## 已知踩坑

- 用 PowerShell 汇总 JSON 时，先把结果赋给变量再管道，避免 `ParserError: An empty pipe element is not allowed.`。
- `docs\` 未纳入 git 时，`git diff --check` 的空输出不能当作校验证据，应直接检查文件内容。
- 查重不要用 `Get-Content -Raw` 通读大文件，改用定向搜索。
- 无法验证的事情不要写成已验证；没有渲染或实机证据就明确说明限制。
